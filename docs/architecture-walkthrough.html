Hookfan · how it works

One webhook in, many services out — without losing any of them

Meta gives an app exactly one callback URL. Hookfan makes that URL a durable fan-out point: it verifies the signature, stores the payload byte-for-byte, and forwards it to every service that subscribed — retrying, tracking, and replaying each attempt. This page walks the path a single payload takes.

2

Ingest reads bytes, not JSON

The signature covers the exact octets Meta sent. Decode first and you can never verify again — key order and whitespace will have changed.

internal/ingest/handler.go order is load-bearing 
// Read the exact bytes before any decoding. Re-marshalling would reorder
// keys and change whitespace, and the signature covers these bytes only.
r.Body = http.MaxBytesReader(w, r.Body, MaxBodyBytes)   // 1 MB cap
body, err := io.ReadAll(r.Body)

if !h.verify(w, r, listener, encSecret, body) {
    return   // 401 — never persisted as a deliverable event
}

keys := router.ExtractRoutingKeys(body, listener.RoutingKeyPath)

event, duplicate, err := h.Store.InsertEvent(r.Context(), store.InsertEventParams{
    ListenerID:  listener.ID,
    RoutingKeys: keys,          // every entry[].id in the batch
    RawBody:     body,          // byte-exact, stored as bytea
    DedupeKey:   crypto.BodyHash(body),
})

Three decisions are hiding in those lines. The MaxBytesReader cap keeps an unauthenticated endpoint from becoming a memory exhaustion vector. The comparison inside verify uses hmac.Equal, which is constant-time, so a mismatch leaks nothing about where the digests diverged. And DedupeKey is the SHA-256 of the body, which is what makes a redelivery idempotent.

A rejected webhook is never stored as deliverable. On a signature mismatch the handler logs the listener slug and a hash of the body — never the body, which may contain message contents.

4

Matching, then collapsing to a set

One event can match a service through several subscriptions. It must still receive exactly one POST.

internal/router/match.go dedup by service, keep provenance 
func (r *MatchResult) addMatch(sub Subscription) {
    // First time we see this service, it joins the delivery set…
    if _, seen := r.SubscriptionsByService[sub.ServiceID]; !seen {
        r.ServiceIDs = append(r.ServiceIDs, sub.ServiceID)
    }
    // …but every matching subscription is still recorded.
    r.SubscriptionsByService[sub.ServiceID] =
        append(r.SubscriptionsByService[sub.ServiceID], sub.ID)
}

A batch carrying WABA_ONE and WABA_TWO, where a service subscribes to each separately, produces one delivery tagged matched_by {1,2}. The unique index on (event_id, service_id) is the second line of defence: even a double-planned event cannot send twice.

Nothing is dropped silently. An event matching no subscription goes to the listener's default subscription. If there isn't one, the planner logs it at WARN — it still marks the event planned, so it isn't retried forever.
5

The claim query, and the version that looks identical

This is the subtlest code in the system. The widely-copied form is wrong in a way that does not show up until several workers run at once.

internal/store/deliveries.go CTE, not IN (SELECT …) 
WITH claimed AS (
    SELECT id FROM deliveries
     WHERE status = 'pending' AND next_attempt_at <= now()
     ORDER BY next_attempt_at          -- inside the lock, not outside
     FOR UPDATE SKIP LOCKED
     LIMIT $2
)
UPDATE deliveries d
   SET status = 'in_flight', attempt_count = d.attempt_count + 1,
       claimed_at = now(), claimed_by = $1
  FROM claimed c
 WHERE d.id = c.id
RETURNING d.*;
The trap. With WHERE id IN (SELECT … FOR UPDATE SKIP LOCKED) the subquery and the outer UPDATE take separate locks. The subquery skips rows locked at that instant, then the outer statement re-locks those ids and blocks on a concurrent worker instead of skipping past it. It does not double-send — the re-checked predicate drops the row — but workers serialise behind each other, which is precisely what SKIP LOCKED was chosen to avoid.
6

How the workers actually start

WORKER_CONCURRENCY goroutines and one reaper, all launched together and all stopped by the same cancelled context.

internal/dispatch/worker.go — Run N workers + 1 reaper, one WaitGroup 
func (d *Dispatcher) Run(ctx context.Context) {
    var wg sync.WaitGroup

    // N identical workers. They are peers — no leader, no partitioning.
    // Which row each one gets is decided by the database, not by us.
    for i := range d.Concurrency {          // default 16
        wg.Add(1)
        go func(id int) {
            defer wg.Done()
            d.worker(ctx, fmt.Sprintf("worker-%d", id))
        }(i)
    }

    wg.Add(1)
    go func() { defer wg.Done(); d.reaper(ctx) }()

    wg.Wait()   // returns only once every goroutine has exited
}

The workers are deliberately identical and uncoordinated. There is no leader election and no sharding of the queue, because FOR UPDATE SKIP LOCKED already decides who gets which row — two workers reaching for the same delivery is not a race to prevent, it is the normal case, and one of them simply skips past. The claimed_by column records which one won, purely so the logs can be read afterwards.

The loop each worker runs

internal/dispatch/worker.go — worker drain fully, then sleep 
for {
    // Drain: keep claiming while FULL batches come back. Without this a
    // backlog of 500 would be metered out 8 per second, one tick at a time.
    for {
        n, err := d.claimAndDeliver(ctx, workerID)   // batch of 8
        if err != nil { break }
        if n < ClaimBatchSize { break }   // short batch ⇒ queue is drained
    }

    // Then idle until something happens.
    select {
    case <-ctx.Done(): return          // shutdown
    case <-d.wake:                     // planner just created deliveries
    case <-ticker.C:                   // 1s fallback poll
    }
}
Two ways to wake, and only one of them is trusted. The planner calls Notify() the moment it inserts deliveries, which is what makes a delivery feel immediate. But that channel is buffered with depth one and a non-blocking send — a notification can be coalesced away under load. The 1 s ticker is what makes the system correct; the notification only makes it fast. Losing every notification would cost latency, not deliveries.

The reaper, and why five minutes

A worker that is killed mid-delivery leaves its row marked in_flight with nobody coming back for it. No error is logged, because nothing errored — the process simply stopped existing. That row would sit there forever.

internal/store/deliveries.go — ReapStuckDeliveries runs every 30s 
UPDATE deliveries
   SET status = 'pending', claimed_by = NULL,
       last_error = 'reclaimed: worker did not report a result'
 WHERE status = 'in_flight'
   AND claimed_at < now() - '5 minutes'::interval;
t+0s worker-3 claims delivery #81 → in_flight, claimed_at=now()
t+2s the pod is evicted mid-request. Nothing is written back.
t+30s reaper ticks. claimed_at is 30s old — too fresh, left alone.
t+4m still inside the window. Still left alone.
t+5m threshold crossed → back to pending, and a worker picks it up.
Why the window has to be generous. The reaper cannot tell a dead worker from a slow one — both look like a row that has been in_flight for a while. Five minutes has to comfortably exceed any service's timeout_ms plus the longest Retry-After sleep it might be honouring. Set it too tight and the reaper hands a still-running delivery to a second worker, and the receiving service gets the same event twice — the exact thing the rest of this design works to prevent.

The cost of the window being generous is bounded: a genuinely crashed delivery waits up to five minutes before being retried. That is the right trade for a fan-out gateway, where a duplicate POST is far more damaging than a late one.

Backoff with full jitter

Each bar is one attempt's ceiling. The actual delay is uniform across the whole bar, starting at zero — press replay to draw a fresh set.

Full jitter means random(0, min(1h, 2s × 2ⁿ)). The range starting at zero is the point: it is what stops a fleet of failed deliveries retrying in lockstep and stampeding a service the moment it recovers.

internal/dispatch/retry.go which responses are worth retrying 
case statusCode >= 200 && statusCode <= 299:
    return Decision{Success: true}

case statusCode == http.StatusTooManyRequests:   // 429
    delay := parseRetryAfter(header.Get("Retry-After"), time.Now())
    return retryOrDead(attempt, maxAttempts, "rate limited", delay)

case statusCode >= 400 && statusCode <= 499:
    // A 400 will still be a 400 on attempt six.
    return Decision{Terminal: true}

case statusCode >= 500:
    return retryOrDead(attempt, maxAttempts, "server error", delay)
8

The failure that makes no noise

Splitting ingest from fan-out buys latency, and introduces one dangerous mode. It is worth knowing before you run this.

Every other failure in this system announces itself. A bad signature returns 401. A dead service turns deliveries red and eventually trips the breaker. This one announces nothing at all.

Why it is invisible

Ingest returns 200 as soon as the row is written — deliberately, because Meta disables slow callback URLs. Fan-out happens later, in the planner. So if the planner stops, every part of the system still looks correct:

Meta sees 200 OK on every webhook …and stops retrying, because delivery succeeded.
Your logs show no errors Nothing errored. A goroutine that stopped doing work isn't an exception.
/api/healthz returns ok The process is alive and serving. That is all it claims.
Your services receive nothing Indistinguishable from a genuinely quiet hour.
The database fills with planned_at IS NULL This is the only place the truth is written down.

The one query that can tell you

Every event carries planned_at, which stays NULL until the planner has built its delivery set. So the age of the oldest unplanned event is the answer: it is zero on a healthy system regardless of traffic, and it climbs in real time the moment the planner stalls.

internal/store/store.go — PlannerLag zero when healthy, even at zero traffic 
SELECT COALESCE(EXTRACT(EPOCH FROM (now() - MIN(received_at))), 0)
  FROM events
 WHERE planned_at IS NULL;

Note what it is not: not a count of unplanned events, and not a rate. A count is high during a healthy burst and low during a slow leak. The age of the oldest unplanned event is unaffected by volume — it answers "how long has something been stuck?", which is the actual question.

Do not use /api/healthz — it deliberately ignores the planner, so a blip never restarts the container
Careful with a k8s readiness probe on /api/readyz pulls the pod from the load balancer — which stops it accepting webhooks too. Alert on it; think twice before gating traffic on it.
The one-line version. Everything else in hookfan fails loudly. This fails quietly, and it is the worst thing that can happen — webhooks accepted, acknowledged to Meta, and forwarded to nobody. planner_lag_seconds is the only signal that separates it from a quiet Tuesday. Put a monitor on it before you put this in production.
